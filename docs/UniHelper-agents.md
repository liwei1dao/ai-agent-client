# UniHelper 多 Agent 团队协作架构

**项目名称**：UniHelper
**文档定位**：回答"UniHelper 是一个 agent 团队而非单个 agent"的架构设计——对外一个管家，对内一支专员团队。是 [UniHelper.md](UniHelper.md) §5「架构演进」中 Orchestrator 的正式展开。
**版本**：v1.0
**日期**：2026-07-01
**状态**：方案稿

---

## 0. 结论先行：可以做，而且已经在路上

**能做，且是成熟范式**（Supervisor / Orchestrator-Worker、Hierarchical Multi-Agent、Agent-as-Tool、A2A、Blackboard）。

更重要的是——**你的现状已经是多 agent 基座**：

```
local_plugins/agents/
├── agent_chat          ← 已有：对话专员
├── agent_sts_chat      ← 已有：端到端语音专员
├── agent_translate     ← 已有：翻译专员
├── agent_ast_translate ← 已有：同传专员
├── agents_server       ← 已有：团队宿主（原生前台服务，后台保活）
└── service_manager     ← 已有：能力/Provider 池
```

现在只需**在它上面加两样**：① 一个 **管家 Agent（Manager）** 作为对外唯一面孔；② 一套 **协作协议**（分派 / 协同 / 自治 / 上报）。再按需扩充专员（日程/邮件/咨询/财务/健康…）。

> 一句话：**App = 一个团队**。用户看到的是「管家」一个人；管家背后是一群各管一摊的「专员」。

## 1. 核心模型：管家 + 专员团队

```
                        用户（只和"管家"对话）
                              │  一条会话 · 一个声音 · 一段记忆
                              ▼
        ┌───────────────────────────────────────────┐
        │            🎩 管家 Manager Agent            │
        │  意图理解 · 任务分派 · 多专员协调 · 结果汇总    │
        │  统一人设与发声 · 持有共享记忆 · 确认闸口       │
        └───────┬───────────────┬───────────────┬─────┘
                │ 分派/协调（A2A）                  │
   ┌────────────┼───────────┬───────────┬─────────┼───────────┐
   ▼            ▼           ▼           ▼         ▼           ▼
📅日程专员   📧邮件专员   📰咨询专员   💰财务专员  ❤️健康专员  💬对话/知识专员
📞通话翻译专员 …（可持续扩充）
   每个专员：独立角色prompt · 自己的工具集(MCP) · 自己的数据域 · 可定时自治
                │ 取用能力
                ▼
   service_manager（Provider 池：LLM/STT/TTS/翻译/向量/视觉…） + MCP 工具
                │
                ▼
   local_db（共享记忆/记录/任务） · 外部服务
```

**管家（Manager）职责**：
- 唯一与用户对话的"人"：无论内部多少专员参与，对外永远一个声音、一条会话。
- 意图识别与路由：判断该找哪个/哪些专员。
- 任务分解与协调：跨域任务拆给多个专员，串行/并行，汇总成一个回复。
- 共享记忆与人设：持有用户画像、偏好、当前上下文，喂给专员，避免重复问。
- **确认闸口**：高风险动作（发邮件/支付/删除）由管家统一向用户求确认。

**专员（Specialist）职责**：
- 各管一个领域，有自己的角色设定、工具集、数据范围。
- 两种工作方式：**被调**（管家分派）+ **自治**（按订阅/调度在后台独立跑，见 §2.3）。
- 只对管家汇报，不直接抢占用户会话。

## 2. 四种协作模式

### 2.1 单点分派（Delegation）
最常见：管家把一个请求交给一个专员。
```
用户：这封邮件帮我回一下 →  管家 →〔分派〕→ 📧邮件专员 起草 → 管家 → 呈现给用户确认
```

### 2.2 多专员协同（Orchestration）
跨域任务，管家分解 → 多专员协作 → 汇总。
```
用户：安排明天下午和张总开会，并邮件通知他
  管家 分解为两步：
    ├─〔并行〕📅日程专员：创建 明天15:00 会议 + 提醒
    └─〔并行〕📧邮件专员：起草给张总的通知邮件
  管家 汇总：「已排明天15:00会议，并拟好通知邮件，要发出吗？」（一次回复）
```

### 2.3 自治后台（Autonomous）
专员按订阅/调度**独立**在后台运行，产出结果**经管家以模板推送进聊天**。
```
每日08:00 → 📰咨询专员 自主搜集+摘要 → 交给管家 → 管家按"资讯"模板 推送到首页聊天
每30分钟 → 📧邮件专员 巡检 → 有重要邮件 → 交管家 → 推送提醒
```
> 这正是「订阅 Tab」在管的东西——每条订阅 = 一个专员的自治任务开关。

### 2.4 上报与确认（Escalation）
专员遇到需用户拍板的事，**不自己找用户**，而是上报管家，由管家在聊天里问。
```
📧邮件专员 拟好回复 →〔需确认〕→ 管家 →「拟了这条回复，发吗？」→ 用户点发送 → 专员执行
💰财务专员 发现异常大额支出 → 上报 → 管家提醒用户
```

## 3. 通信与协议（A2A）

- **任务信封（Task Envelope）**：agent 间传递的标准结构
  ```
  { taskId, from, to, intent, params, context,   // context = 相关记忆/会话片段
    needConfirm, deadline, priority }
  ```
- **专员即工具（Agent-as-Tool）**：每个专员对管家注册为一个"可调用能力"，管家用统一的工具调用接口分派（复用现有 MCP/ToolCall 机制）。
- **共享黑板 / 记忆（Blackboard）**：`local_db` 里的共享记忆与当前上下文，专员读写同一份，避免"日程专员不知道用户刚跟对话专员说过的话"。
- **事件回传**：专员 `onProgress / onResult / onNeedConfirm / onError` → 管家；管家决定如何汇总与呈现。

## 4. 落到现有架构（增量，不推翻）

```
┌──────────────────────────────────────────────────────────┐
│  Flutter UI：首页聊天（只见管家）/ 订阅（专员自治开关）/ 生活 / 我的 │
└───────────────┬──────────────────────────────────────────┘
                │ Pigeon 命令 ↓ / Event 事件 ↑
┌───────────────▼──────────────────────────────────────────┐
│  agents_server（团队宿主 · 原生前台服务 · 后台保活）★升级     │
│   + 🎩 Manager Agent（新增：路由/协调/汇总/确认/共享记忆）     │
│   + 调度/触发引擎（定时·事件 → 唤起对应专员）                  │
│   + A2A 消息总线 + 任务图                                    │
├───────────────────────────────────────────────────────────┤
│  专员 Agents：                                              │
│   已有 agent_chat / agent_sts_chat / agent_translate /      │
│        agent_ast_translate                                 │
│   新增 agent_schedule / agent_email / agent_news /          │
│        agent_finance / agent_health …                      │
├───────────────────────────────────────────────────────────┤
│  service_manager（Provider 池） + MCP 工具 + local_db（共享） │
└───────────────────────────────────────────────────────────┘
```

- **agents_server 升级为"团队宿主"**：内置 Manager + 调度引擎 + A2A 总线；现有四专员平滑纳入。
- **现有 Agent 基础模板保持不动**（翻译等所有 agent、以及后续硬件配合 agent 的共同底座）：新层通过 `SpecialistAdapter` **包住**现有 agent，不改写、不取代（详见 [UniHelper-agents-protocol.md](UniHelper-agents-protocol.md) §0.1）。
- **模型分层**：管家用强模型做规划路由；专员可用便宜/专用模型（成本与延迟优化）。能直达单专员就不做多跳。
- **数据**：复用 §9 的 `assistants / tasks / records`；新增 agent 运行态（会话、任务图、专员状态）。
- **渐进落地**：第一步先让 Manager 只做"路由"包住现有 4 个专员；再逐个加新专员与协同能力。不必一步到位。

## 5. 关键决策与权衡

| 议题 | 取舍 |
|------|------|
| **单一外部面孔** | 无论内部几个专员参与，对用户永远一个声音、一条会话。管家负责收敛。 |
| **路由成本/延迟** | 管家"规则 + 轻模型"快速路由，复杂任务才上强模型规划；避免无谓多跳。 |
| **安全闸口** | 发邮件/支付/删除等高风险动作，专员必须经管家走**用户确认**，不得自动执行（可设高级开关）。 |
| **并发与数据一致** | 共享资源（日历/账本）需协调与去重，避免两个专员同时写冲突（任务图 + 锁）。 |
| **可观测/可追溯** | 每个专员的调用与结果落 `records`，在「生活/动态」可追溯"谁做了什么"。 |
| **可解释** | 推送/回执可标注来源专员（📅日程/📧邮件），让"团队协作"可感知但不喧宾夺主。 |

## 6. UI 呈现：团队感，但不吵

- **默认**：用户只感到"一个很能干的管家"——一个声音、一条会话。
- **可选团队感**：主动推送与回执里标注来自哪个专员（`〔📅日程专员〕`），复杂任务可显示"日程专员、邮件专员正在协作…"的过程动效。
- **「我的 → 助手管理」= 团队花名册**：启用/停用/配置每个专员——这与现有设计完美契合（每个专员就是一个"助手"）。
